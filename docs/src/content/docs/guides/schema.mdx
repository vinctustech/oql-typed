Your schema is the source of truth. Define it once in TypeScript with `defineSchema(...)` and both runtime OQL and compile-time types fall out of it.

## Shape of a schema

A schema is a single object passed to `defineSchema(...)`. Each entry maps an **entity name** (the key) to an entity definition produced by `entity(...)`. Relations reference other entities by **string literal**, so there are no circular-import problems.

```typescript
import { defineSchema, entity, uuid, text, boolean } from '@vinctus/oql-typed'

export const schema = defineSchema({
  category: entity('categories', {
    id:      uuid().primaryKey(),
    name:    text(),
    slug:    text(),
    enabled: boolean(),
  }),
})
```

`entity(...)` has two forms:

- **`entity(fields)`** — the entity name doubles as the table name.
- **`entity(tableName, fields)`** — use when your SQL table name differs from the entity name.

The **entity name** (used in `query(db, 'category')`, OQL strings, and relation targets) is the **key** in the `defineSchema({...})` object — not an argument to `entity()`.

<Aside type="note">
`defineSchema` is just an identity function with a `const` generic — it preserves literal types so TypeScript can infer everything (entity names, enum values, field shapes) without manual annotations. A plain object works too, but `defineSchema` is preferred.
</Aside>

## Column types and modifiers

### Built-in column constructors

```typescript
import {
  uuid, text, integer, bigint, float, decimal,
  boolean, timestamp, date, time, interval,
  json, textArray, integerArray, enumType,
} from '@vinctus/oql-typed'
```

| Constructor | TypeScript type | PostgreSQL type |
|-------------|-----------------|-----------------|
| `uuid()` | `string` | `uuid` |
| `text()` | `string` | `text` |
| `integer()` | `number` | `integer` |
| `bigint()` | `bigint` | `bigint` |
| `float()` | `number` | `real` / `double precision` |
| `decimal(precision?, scale?)` | `bigint` | `decimal(p,s)` |
| `boolean()` | `boolean` | `boolean` |
| `timestamp()` | `Date` | `timestamp` |
| `date()` | `Date` | `date` |
| `time()` | `string` | `time` |
| `interval()` | `Interval` | `interval` |
| `json<T = unknown>()` | `T` | `json` / `jsonb` |
| `textArray()` | `string[]` | `text[]` |
| `integerArray()` | `number[]` | `integer[]` |
| `enumType<T>(name, values)` | `T` | custom enum |

#### Interval columns

`Interval` is a distinct type rather than `string`, so an interval column can be added to a timestamp, scaled, and compared against another interval without a cast — see [Arithmetic](/guides/expressions/#arithmetic). A text column can never stand in for one.

```typescript
shift: entity('shifts', {
  id:          uuid().primaryKey(),
  startsAt:    timestamp().column('starts_at'),
  duration:    interval(),                              // Interval
  gracePeriod: interval().column('grace_period').nullable(), // Interval | null
})

await db.shift.insert({ startsAt, duration: '30 minutes', store: storeId })
```

Writes take the PostgreSQL interval syntax you write (`'30 minutes'`, `'1 day 02:30:00'`); the backend casts it on the way in. Reads stay strict.

`Interval` is `IntervalObject | IntervalString`, because the runtime shape depends on where the value is read:

| Read | Runtime value |
|------|---------------|
| A top-level `interval` column under PostgreSQL | An `IntervalObject` — the driver parses it with `postgres-interval`, setting only the non-zero fields: `{ days: 1, hours: 2, minutes: 30 }`. |
| The same column inside a `oneToMany`/`manyToMany` projection | A string in PostgreSQL interval syntax — OQL builds sub-collections with `to_json()`, which renders the interval as text before the driver sees it. |
| Any `interval` column under `createPetraDB` | A string in ISO-8601 duration form: `'PT30M'`. |

So narrow before you use one:

```typescript
const text = typeof shift.duration === 'string' ? shift.duration : shift.duration.toISOString()
```

Installing `keepIntervalAsString` (see [Result type parsing](#result-type-parsing)) makes every PostgreSQL read a string, collapsing the first case into the second.

### Modifiers

Chain modifiers after a column constructor:

```typescript
user: entity('users', {
  id:          uuid().primaryKey(),                             // marks PK
  firstName:   text().column('first_name'),                     // renames column
  email:       text(),
  lastLoginAt: timestamp().column('last_login_at').nullable(),  // nullable + rename
  createdAt:   timestamp().column('created_at').default(),      // NOT NULL DEFAULT now()
})
```

| Modifier | Effect |
|----------|--------|
| `.primaryKey()` | Marks this column as the primary key. |
| `.nullable()` | Adds `\| null` to the inferred type; the column is allowed to be `NULL`. |
| `.default()` | The database supplies a value when the insert omits the column. |
| `.column('alias')` | Uses a different database column name than the TypeScript field name. |

<Aside type="note">
`.nullable()` changes both the TypeScript type and the underlying DM definition. Mismatching nullability between your schema and the database is one of the most common bugs typed queries catch.
</Aside>

### Columns with database defaults

A column declared `NOT NULL DEFAULT ''` (or `DEFAULT 0`, `DEFAULT now()`) is never `null`, yet you should not have to pass it on every insert. `.default()` says exactly that: the column becomes **optional on insert** while its inferred type stays non-null on read. No default value is stored in the schema — the database owns it.

```typescript
post: entity('posts', {
  id:        uuid().primaryKey(),
  title:     text(),
  slug:      text().default(),                             // NOT NULL DEFAULT ''
  createdAt: timestamp().column('created_at').default(),   // NOT NULL DEFAULT now()
})

await db.post.insert({ title: 'Hello' })       // slug and createdAt omitted
const row = await db.post.findOneById(postId)
// row.slug      => string   (not string | null)
// row.createdAt => Date     (not Date | null)
```

<Aside type="caution">
`.default()` does not make a column nullable — passing `null` for one is still a type error. Chain both (`.nullable().default()`) for a column that is nullable *and* defaulted.
</Aside>

## Enums

```typescript
type PostStatus = 'DRAFT' | 'PUBLISHED' | 'ARCHIVED'

post: entity('posts', {
  id:     uuid().primaryKey(),
  title:  text(),
  status: enumType<PostStatus>('PostStatus', ['DRAFT', 'PUBLISHED', 'ARCHIVED']),
})
```

Operators reject invalid enum values at compile time:

```typescript
eq(db.post.status, 'PUBLISHED')   // ✓
eq(db.post.status, 'APPROVED')    // ✗ type error
```

## Relations

Relations target other entities **by string literal** — the same name you use as the key in `defineSchema(...)`. No `() => ref` thunks, no circular-import worries.

| Constructor | Shape at the type level | OQL emits |
|-------------|-------------------------|-----------|
| `manyToOne(target, { column })` | One target row | LEFT JOIN |
| `oneToMany(target)` | `Target[]` | lateral subquery |
| `manyToMany(target, { junction })` | `Target[]` | lateral subquery with junction join |
| `oneToOne(target, { reference? })` | One target row | lateral subquery (single) |

### manyToOne — foreign key

```typescript
post: entity('posts', {
  id:       uuid().primaryKey(),
  title:    text(),
  author:   manyToOne('user',     { column: 'author_id' }),
  category: manyToOne('category', { column: 'category_id' }).nullable(),
}),
```

With `manyToOne`, field access builds **dotted paths** that keep their types:

```typescript
db.post.author             // RelationFieldRef
db.post.author.id          // FieldRef<string>
db.post.author.email       // FieldRef<string> (one-level hop)
db.post.category.id        // FieldRef<string | null> (propagates nullability)
```

### oneToMany — reverse FK

```typescript
user: entity('users', {
  id:    uuid().primaryKey(),
  posts: oneToMany('post'),
}),
```

### manyToMany — junction table

```typescript
post: entity('posts', {
  id:   uuid().primaryKey(),
  tags: manyToMany('tag', { junction: 'post_tags' }),
}),

tag: entity('tags', {
  id:    uuid().primaryKey(),
  name:  text(),
  posts: manyToMany('post', { junction: 'post_tags' }),
}),
```

### oneToOne

```typescript
user: entity('users', {
  id:      uuid().primaryKey(),
  profile: oneToOne('profile'),
}),

profile: entity('profiles', {
  id:      uuid().primaryKey(),
  user:    manyToOne('user', { column: 'user_id' }),
  bio:     text(),
  website: text().nullable(),
}),
```

The optional `{ reference }` option points at the field on the target that holds the FK back — useful when the owning side has a non-default name:

```typescript
user: entity('users', {
  id:      uuid().primaryKey(),
  vehicle: oneToOne('vehicle', { reference: 'driver' }).nullable(),
}),
```

### Self-referencing manyToOne

Self-references work out of the box because targets are strings:

```typescript
comment: entity('comments', {
  id:     uuid().primaryKey(),
  body:   text(),
  parent: manyToOne('comment', { column: 'parent_id' }).nullable(),
}),
```

### Two relations to the same target

Just give them different field names and column aliases:

```typescript
post: entity('posts', {
  id:         uuid().primaryKey(),
  title:      text(),
  author:     manyToOne('user', { column: 'author_id' }),
  reviewedBy: manyToOne('user', { column: 'reviewed_by_id' }).nullable(),
}),
```

## Wiring up the runtime

`createPostgresDB(schema, connection)` returns a typed `db` handle. The schema you pass is the same object you got from `defineSchema(...)`, and it is the only data model — the factory derives the OQL data model from it and hands that to the backend.

```typescript
import { createPostgresDB } from '@vinctus/oql-typed'
import { schema } from './schema.js'

export const db = createPostgresDB(schema, {
  host, port, database, user, password,
})
```

`db.post.id`, `db.post.author.email`, `db.post.select(...)`, etc. all become available with full type inference. Call `db.close()` on shutdown to release the connection pool.

### Result type parsing

The driver hands some column types back as raw text. `typeParsers` maps a PostgreSQL type OID to the parser that converts it, and the parsers are installed on the driver instance this package uses — you need no `pg` dependency of your own. Nothing is installed unless you ask for it.

```typescript
import {
  PostgresTypeOid,
  createPostgresDB,
  keepIntervalAsString,
  keepJsonAsString,
  parseInt8AsNumber,
  parseTimestampAsUtcDate,
} from '@vinctus/oql-typed'

export const db = createPostgresDB(schema, {
  host, port, database, user, password,
  typeParsers: {
    [PostgresTypeOid.INT8]: parseInt8AsNumber,            // bigint as a number, not a string
    [PostgresTypeOid.TIMESTAMP]: parseTimestampAsUtcDate, // zoneless timestamp read as UTC
    [PostgresTypeOid.JSON]: keepJsonAsString,             // json left unparsed
    [PostgresTypeOid.INTERVAL]: keepIntervalAsString,     // interval as text, matching nested reads
  },
})
```

`PostgresTypeOid` also carries `TIMESTAMPTZ` and `NUMERIC` for parsers you write yourself; any OID and `(value: string) => unknown` pair works.

For tests, `createPetraDB(schema)` gives the same handle backed by the in-memory engine — install the optional `@vinctus/oql-petradb` peer to use it.

```typescript
import { createPetraDB } from '@vinctus/oql-typed'
import { schema } from './schema.js'

const db = createPetraDB(schema)
```

If you need to construct the OQL instance yourself — an unusual backend, a shared instance, custom pool wiring — `typedOQL(instance, schema)` is the escape hatch. You own the instance and its data model:

```typescript
import { typedOQL } from '@vinctus/oql-typed'
import { OQL_PG } from '@vinctus/oql-pg'
import { schema } from './schema.js'

const instance = new OQL_PG(dataModel, host, port, database, user, password, false, 7200000, 10)

export const db = typedOQL(instance, schema)
```

## The full blog schema

Every column type, every relation kind, every modifier. The examples elsewhere in these docs draw from this schema.

```typescript
import {
  defineSchema, entity,
  uuid, text, integer, bigint, float, decimal,
  boolean, timestamp, date, time, interval,
  json, textArray, integerArray, enumType,
  manyToOne, oneToMany, manyToMany, oneToOne,
} from '@vinctus/oql-typed'

export type UserRole = 'ADMIN' | 'AUTHOR' | 'READER'
export type PostStatus = 'DRAFT' | 'PUBLISHED' | 'ARCHIVED'

export const schema = defineSchema({
  user: entity('users', {
    id:          uuid().primaryKey(),
    email:       text(),
    firstName:   text().column('first_name'),
    lastName:    text().column('last_name'),
    role:        enumType<UserRole>('UserRole', ['ADMIN', 'AUTHOR', 'READER']),
    enabled:     boolean(),
    rating:      float().nullable(),
    metadata:    json().nullable(),
    lastLoginAt: timestamp().column('last_login_at').nullable(),
    profile:     oneToOne('profile'),
    posts:       oneToMany('post'),
    comments:    oneToMany('comment'),
  }),

  profile: entity('profiles', {
    id:      uuid().primaryKey(),
    user:    manyToOne('user', { column: 'user_id' }),
    bio:     text(),
    website: text().nullable(),
  }),

  category: entity('categories', {
    id:   uuid().primaryKey(),
    name: text(),
    slug: text(),
  }),

  tag: entity('tags', {
    id:    uuid().primaryKey(),
    name:  text(),
    posts: manyToMany('post', { junction: 'post_tags' }),
  }),

  post: entity('posts', {
    id:             uuid().primaryKey(),
    title:          text(),
    slug:           text(),
    body:           text(),
    status:         enumType<PostStatus>('PostStatus', ['DRAFT', 'PUBLISHED', 'ARCHIVED']),
    featured:       boolean(),
    viewCount:      integer().column('view_count'),
    wordCount:      bigint().column('word_count'),
    readingTime:    decimal(4, 2).column('reading_time').nullable(),
    createdAt:      timestamp().column('created_at'),
    publishedAt:    timestamp().column('published_at').nullable(),
    publishedOn:    date().column('published_on').nullable(),
    publishTime:    time().column('publish_time').nullable(),
    editWindow:     interval().nullable(),
    keywords:       textArray(),
    visitHistogram: integerArray().column('visit_histogram'),
    metadata:       json().nullable(),
    author:         manyToOne('user',     { column: 'author_id' }),
    reviewedBy:     manyToOne('user',     { column: 'reviewed_by_id' }).nullable(),
    category:       manyToOne('category', { column: 'category_id' }).nullable(),
    comments:       oneToMany('comment'),
    tags:           manyToMany('tag', { junction: 'post_tags' }),
  }),

  comment: entity('comments', {
    id:        uuid().primaryKey(),
    body:      text(),
    createdAt: timestamp().column('created_at'),
    post:      manyToOne('post',    { column: 'post_id' }),
    author:    manyToOne('user',    { column: 'author_id' }),
    parent:    manyToOne('comment', { column: 'parent_id' }).nullable(),
  }),
})
```

What's exercised here:

- **All scalar column types**: uuid, text, integer, bigint, float, decimal, boolean, timestamp, date, time, interval, json, textArray, integerArray.
- **Enum columns** (`UserRole`, `PostStatus`) with compile-time-checked values.
- **All modifiers**: `.primaryKey()`, `.nullable()`, `.column()`.
- **Every relation kind**: `manyToOne`, `oneToMany`, `manyToMany`, `oneToOne`.
- **Two `manyToOne`s to the same target** (`post.author` and `post.reviewedBy`).
- **Self-referencing `manyToOne`** (`comment.parent`).
